# Moving the receiver's data to its own database ("client-data")

Written 3 Nov 2026 for Petrus, revised the same day after Cowork's review. Workstream G. Every step says who clicks, what you should see, and how to go back. Nothing is deleted until the very last step, which needs your separate yes at least 7 days later.

## Why

Today the receiver's call data (Sendsteps and EconoWind) sits in the same Postgres as Paperclip, under the one owner login whose password is in old agent run logs. Moving it to its own Postgres with its own two logins means: that password no longer unlocks client data, the receiver gets a login that cannot administer anything, and anyone who only needs to look gets a read-only login.

## How the migration runs: inside Railway, nothing public, nothing typed

The shared Postgres has no public endpoint today and must not get one (its password has leaked into run logs). So the copy runs inside Railway, on the private network, as a temporary service built from this repository. Its step is chosen by one variable, its output is read in its deploy log with every connection string masked, and the service is deleted at the end. Both connection strings are Railway references to the two Postgres services, and both new passwords are generated by Railway as shared variables and referenced from there. Nobody types, pastes or sees a secret.

## What you will have at the end

| Thing | Where |
|---|---|
| A Railway Postgres service named `client-data`, daily backups and point-in-time recovery on from day one | Railway, project gracious-unity |
| Login `receiver_app`: the receiver's own login, reads and writes its tables, cannot create logins or databases | password: shared variable `RECEIVER_APP_PASSWORD` |
| Login `receiver_ro`: read-only, for reports and checks | password: shared variable `RECEIVER_RO_PASSWORD` |
| The receiver running on `CLIENT_DATABASE_URL`; `/health` says `"source":"client-data"` | variable on the receiver service, built from references |
| The old tables still in the shared Postgres, untouched, for 7 days | gracious-unity Postgres |

## Timing

A quiet window of about 30 minutes: not 15:00 to 22:00 Amsterdam on a weekday, not around 07:00 UTC (Reconciliation Checker), not around 20:55 UTC. EconoWind chat runs around the clock, so a webhook may land during the switch; the delta copy in step 7 picks up new rows. **Rows that are updated (not added) between the copy and the switch are not re-copied**, so keep that gap to a few minutes: run step 6 immediately before step 7.

## Step 0. Manual backup of the shared Postgres (Petrus, Railway, 2 minutes)

Open the `Postgres` service in gracious-unity, Backups tab, create a manual backup. Readback: the new backup's time and size shown in the tab. Paste both in the chat. Do not continue until it is there.

## Step 1. Create the new Postgres (Petrus, Railway, 5 minutes)

In project gracious-unity: New, Database, PostgreSQL. Name the service exactly `client-data` (the references below use that name). When it is up, open its Backups tab: enable daily backups and click Enable PITR (as on 28 Oct for the shared database). Readback: the Backups tab shows the PITR picker, and the service's variables include `WAL_ARCHIVE_*`.

## Step 2. Two shared variables, generated by Railway (Petrus, 2 minutes)

Project Settings, Shared Variables, environment production. Add:

| Name | Value |
|---|---|
| `RECEIVER_APP_PASSWORD` | `${{secret(32)}}` |
| `RECEIVER_RO_PASSWORD` | `${{secret(32)}}` |

Railway replaces `${{secret(32)}}` with a random 32-character value once (the same mechanism that made `BETTER_AUTH_SECRET` for Paperclip). Readback: both names listed; do not open the values. They survive the deletion of the temporary service.

## Step 3. The temporary migration service (Petrus, 5 minutes)

1. New, GitHub Repo, this repository (`Scala-Auxilio/retell-webhook-receiver`), branch `main` (after this PR is merged). Name the service `migrate`.
2. Settings, Deploy, Start Command: `node scripts/migrate-client-db.mjs`
3. Settings, Networking: no public domain. Leave it unexposed.
4. Variables (Raw Editor), exactly:

```
MIGRATION_SERVICE=1
MIGRATION_STEP=idle
SOURCE_DATABASE_URL=${{Postgres.DATABASE_URL}}
CLIENT_ADMIN_DATABASE_URL=${{client-data.DATABASE_URL}}
RECEIVER_APP_PASSWORD=${{shared.RECEIVER_APP_PASSWORD}}
RECEIVER_RO_PASSWORD=${{shared.RECEIVER_RO_PASSWORD}}
```

5. Deploy. Readback in the deploy log: `=== idle ===`, `nothing to do`, then `migration service idle: set MIGRATION_STEP to the next step and redeploy`. The service stays up and does nothing until told.

If the log shows `The server does not support SSL connections`, add `DB_SSL=false` to this service and redeploy; the private network does not need TLS.

From here on, each step is: change `MIGRATION_STEP`, deploy, read the log. Each step prints `=== <step> (<time>) ===` first, and connection strings only as `postgresql://user:***@host:port/db`.

## Step 4. Logins: `MIGRATION_STEP=roles`

Readback: six `ok` lines (or `skip ... already exists` on a rerun). Creates `receiver_app` (login, no superuser, cannot create databases or logins), `receiver_ro` (same, read-only), lets both connect, lets `receiver_app` create tables, and makes every table `receiver_app` creates readable by `receiver_ro`.

## Step 5. Empty tables and counts before: `MIGRATION_STEP=schema,counts`

Readback: the "Database table ... ready" lines, `schema created as receiver_app`, then a table of row counts: source counts, target counts (all 0), max ids. Paste the table in the chat; it holds no personal data.

## Step 6. Copy and verify: `MIGRATION_STEP=copy,verify`

Readback: per table `copied N rows (up to id X)` and `N new rows copied`, then the counts table ending in `MATCH`. If it ends in `DIFFERS` (a webhook arrived meanwhile), redeploy the same step; copy only takes what is new. Go to step 7 immediately after `MATCH`.

## Step 7. Switch the receiver (Petrus, Railway, 5 minutes, then the delta)

1. On the `retell-webhook-receiver` service, add one variable, built only from references:

```
CLIENT_DATABASE_URL=postgresql://receiver_app:${{shared.RECEIVER_APP_PASSWORD}}@${{client-data.PGHOST}}:${{client-data.PGPORT}}/${{client-data.PGDATABASE}}
```

2. Deploy. Readback in the receiver's deploy log: `Database: client-data (CLIENT_DATABASE_URL)` and the "ready" lines. Open `/health`: `"source":"client-data"`.
3. Straight away on the `migrate` service: `MIGRATION_STEP=copy,verify`, deploy. This picks up rows written to the old database between step 6 and the receiver's restart. Readback: `MATCH`, or a few rows more on the target only (they arrived after the switch, which is correct).
4. Readback by Claude Code from Railway: the receiver's deploy log and HTTP log, no connection errors, and the next Reconciliation Checker run at 07:00 UTC reporting normal counts.

## Step 8. Prove the logins: `MIGRATION_STEP=prove`

Readback: a table with PASS on every row and `PROOF PASSED`. As `receiver_ro`: SELECT works; INSERT, UPDATE, DELETE, CREATE TABLE and DROP TABLE are refused. As `receiver_app`: SELECT and a rolled-back INSERT work; CREATE ROLE, CREATE DATABASE, ALTER SYSTEM and COPY to a server file are refused. Paste the table; it contains no data.

## Step 9. Delete the migration service (Petrus)

Settings, Delete service `migrate`. The shared variables stay (the receiver references one of them). Readback: the project shows Postgres, client-data, Paperclip and the receiver only.

## Step 10. Seven days later: drop the old tables (needs your yes)

Only after seven days on `client-data` with no problem, a fresh manual backup of the shared Postgres (as in step 0), and your explicit yes: run `sql/drop-old-receiver-tables.sql` against the **shared** Postgres through the Cowork session or a one-off `migrate`-style service. It drops the seven receiver tables there and nothing else. Until then the old data stays exactly where it is.

## Rollback

| When | What to do | What you lose |
|---|---|---|
| Steps 0 to 6 | Nothing to undo; the receiver never touched the new database. Delete `client-data` and `migrate` if you want. | Nothing |
| After step 7, within the window | Remove `CLIENT_DATABASE_URL` from the receiver and deploy. The receiver is back on the shared database, whose tables were never changed. | Rows received after the switch exist only on `client-data`. To bring them back, give the `migrate` service the two URLs swapped (`SOURCE_DATABASE_URL=${{client-data.DATABASE_URL}}`, `CLIENT_ADMIN_DATABASE_URL=${{Postgres.DATABASE_URL}}`) and run `copy`: the copy is symmetric and only adds what is missing. Rows updated in the gap are not re-copied either way. |
| Later | Same as above, plus the swapped copy for the days in between. | Nothing added; updates made in the gap on either side are not merged. |

## Checks Claude Code does from Railway (read-only)

Deploy log lines of the `migrate` service per step (masked), `Database: client-data` on the receiver, `/health` source, no connection errors after the switch, the Reconciliation Checker's next run normal, and the `client-data` Postgres showing PITR variables and its bucket. Claude Code never reads variable values.
